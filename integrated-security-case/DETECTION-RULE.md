# AUTH-001 — Repeated failures followed by a successful sign-in

**Status:** Implemented and regression-tested against the synthetic Northstar Solutions fixture.  
**Platform:** Python standard library; educational, offline analysis.  
**Telemetry:** CSV authentication events, not a direct Microsoft Entra ID connector.

## Detection objective

Identify a **user + source IP** with at least `N` failed sign-ins during an `M`-minute window immediately preceding a **later successful sign-in** from the same pair.

The default rule uses **three or more failures in ten minutes**. The rule is an **investigation lead**, not a verdict that credentials were stolen or that the success was unauthorized.

## Input and logic

Required CSV fields: `timestamp`, `user`, `source_ip`, `application`, and `status`. Values for `status` must be `failed` or `success`. The bundled fixture also supplies `error_code` and `interactive`, but these additional fields are **not evaluated by this detector**.

1. Read the events and parse timestamps. The current example requires **naive timestamps that all refer to the same documented scenario timezone**.
2. Sort the events chronologically and group by user and source IP.
3. Within each group, discard failures older than the configured lookback window.
4. On a success, count only failures **strictly earlier** than that success. If the count meets the threshold, report the pair and times.
5. Clear that pair's failure sequence after **each** success. Other users or IPs are not combined.

Equal timestamps are not assumed to establish order. The inclusive time-window boundary is evaluated precisely; duplicate input rows count as separate events. Neither user identity nor source IP alone establishes a session.

## Reproduce the rule

From the repository root using Python 3.10+:

```sh
python integrated-security-case/scripts/analyze_signin_case.py
python integrated-security-case/scripts/analyze_signin_case.py --format json
python integrated-security-case/scripts/analyze_signin_case.py --format json --threshold 7
python -m unittest discover -s integrated-security-case/tests -v
```

The default synthetic fixture contains 12 events. The default rule should emit **one review finding**, describing six failures before a success at **2026-09-10 08:15:19** for `emma.lee@northstar.example` from `198.51.100.23`. A threshold of seven produces **zero findings** for this fixture.

The `--format json` flag prints one JSON document to standard output. Example extraction into a local file:

```sh
python integrated-security-case/scripts/analyze_signin_case.py --format json > auth-findings.json
```

The exported structure includes:

```json
{
  "schema_version": 1,
  "rule_id": "AUTH-001",

  "rule": {
    "minimum_failures": 3,

    "group_by": ["user", "source_ip"],
```

## Validation and negative cases

| Test | Expected behavior |
|---|---|
| Six failures, then a later success, same user/IP | One review finding |
| Success precedes failures | No match |
| Failure events are outside the window | No match |
| Same user, different source IP | No match |
| Same IP, different user | No match |
| Success followed by another success | No repeated match from cleared failures |
| Failures only, without success | No match |
| Equal timestamps for failures and success | Equal timestamps do not imply failure-before-success |
| Non-finite or non-positive time window | Reject configuration |
| Threshold above matching failure count | No finding |

See [unit tests](tests/test_auth_patterns.py) and [CLI/JSON tests](tests/test_input.py).

## Analyst triage and limitations

A legitimate user mistyping a password before successfully signing in may match. Shared VPN egress, network address translation, remote work, clock inconsistencies, noisy data, duplicate events, and incomplete telemetry may also affect interpretation.

Before taking containment action, check **account owner confirmation**, MFA outcome, Conditional Access results, source/device context, session identifiers, mailbox changes, and other account activity. This synthetic CSV **does not include enough fields** to establish those facts.

The bundled dataset is not a production sign-in export, and this Python rule has **not been deployed to Microsoft Sentinel, Splunk, or Microsoft Entra ID**. There are no measured false-positive rates, precision/recall metrics, or production service-level guarantees. Any real integration needs schema mapping, timestamp validation, independent reference cases, privacy review, and access-control safeguards.
